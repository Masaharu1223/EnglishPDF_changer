## Q1. アップロードしてから、最初のチャンクが Claude に届くまで、どう流れるか

**A.** 今のコードでは、Claude に届くまでに、ブラウザとサーバーの往復が4回ある。

PDF / TXT の場合の流れ:

1. **ブラウザ**: ファイルをメモリに読み込み、base64 の文字列に変える(サイズは約1.3倍になる)。
2. **ブラウザ → サーバー**: `/api/extract` に、ファイル全体を JSON で送る。これがアップロード。
3. **Vercel**: 本文を最後まで受け取ってから、関数を起動する。
4. **サーバー**: JSON を読み、PDF / TXT から本文のテキストを取り出して返す。
5. **ブラウザ → サーバー**: `/api/process`(`action: "split"`)にテキストを送り直し、チャンクに分けてもらう。
6. **ブラウザ → サーバー**: `/api/usage` で、残りの使用量を確かめる。
7. **ブラウザ → サーバー**: チャンク1を `/api/process`(`action: "translate"`)に送る。サーバーは使用量を引いてから、**ここで初めて Claude に送る**。

貼り付けたテキストの場合は、1〜4 がなく、5 から始まる。

8 以降は、ブラウザがチャンクを1つずつ送り、1つ返ってくるたびに次を送る(ループはブラウザ側にある)。

関係するコード:
- `src/app/page.tsx` の `handleFileSelected`(1, 2)と `processText`(5〜7 とループ)
- `src/app/api/extract/route.ts`(4)
- `src/app/api/process/route.ts`(5, 7)

## Q2. アップロードの途中で通信が切れたら、どうなるか

**A.** サーバー側では何も起きない。ブラウザにはエラーが表示され、もう一度アップロードすればやり直せる。

- **サーバー**: Vercel は本文を最後まで受け取るまで関数を起動しない。そのため、次のどれも行われない。
  - ログインの確認
  - テキストの抽出
  - 使用量を引くこと(課金されない)
  - DB への書き込み
- **ブラウザ**: `fetch` が通信エラーで失敗し、`handleFileSelected` の `catch` でエラーを表示する。
  - 表示されるのはブラウザの生のメッセージ(Safari なら「Load failed」など)で、分かりにくい。
- 中途半端な状態は残らない。

## Q3. ログイン(セッション)の確認は、アップロードの前か後か

**A.** 後。アップロードが終わってから確認する。

- ブラウザは、Cookie(セッション)をリクエストの最初に送っている。けれども、Vercel はファイルを全部受け取るまで関数を起動しないので、サーバーが確認できるのは受け取り終わった時点になる。
- そのため、アップロード中にちょうどセッションの期限(2時間)が来ると、未ログインとして扱われる。
  - チケット(#54)も出ないし、履歴にも保存されない。
- ブラウザ側で Cookie の期限が先に切れていると、Cookie 自体が送られない。この場合も、未ログインとして扱われる。

アップロードの前に確認する方法は、Issue #57 で検討する。前に確認しても、その結果をあとのアップロードに引き継ぐには、何か証拠を渡す必要がある。つまり、チケットと同じものが要る。

## Q4. どんなエンドポイントがあり、それぞれのリソースとメソッドは何か

**A.** 今は7つ(ログインの窓口を含む)ある。ストリーミングの PR 2 で、`/api/translations` が1つ加わる予定。

### 用語
- **エンドポイント**: サーバーの窓口。「URL」と「メソッド」の組で1つの窓口になる。同じ URL でも、メソッドが違えば別の窓口。
- **リソース**: その URL が表している「もの」。たとえば `/api/documents` なら「教材(履歴)」。URL は名詞で書くのが基本で、何をするかはメソッドで表す。
- **メソッド**: そのリソースに何をするか。このアプリで使っているのは次の3つ。更新に使う PUT と PATCH は、今は使っていない。
  - GET: 読むだけ。何も変えない
  - POST: 新しく作る、または処理を頼む
  - DELETE: 消す

### 今あるエンドポイント
1. **`/api/auth/...`(GET・POST)**
   - リソース: ログインのセッション。中身は Better Auth(ライブラリ)が全部作る。
   - この下に、ログイン中かを聞く窓口(`get-session`)、Google ログインを始める窓口、Google から戻ってくる窓口、ログアウトの窓口などがまとまっている。
   - 呼ぶところ: ログインボタン(`AuthButton`)など、`src/lib/auth-client.ts` を使う画面の部品。
2. **`/api/usage`(GET)**
   - リソース: 今日の使用量。残りの翻訳文字数と、音声が使えるかを返す。読むだけなので GET。
   - 呼ぶところ: `src/components/UsageProvider.tsx`
3. **`/api/extract`(POST)**
   - リソースというより「処理」の窓口。PDF / TXT のファイルを受け取り、本文を取り出して返す。
   - 呼ぶところ: トップ画面でファイルを選んだとき(`src/app/page.tsx` の `handleFileSelected`)
4. **`/api/process`(POST)**
   - 処理の窓口。送る中身の `action` によって、2つの仕事をする。
     - `split`: 本文をチャンクに分ける
     - `translate`: チャンクを1つ翻訳する(翻訳の前に使用量を予約する)
   - 呼ぶところ: トップ画面(`processText`)。翻訳中に何回も呼ばれる。
5. **`/api/documents`(POST)**
   - リソース: 教材(履歴)の集まり。そこに新しい教材を1件保存する。
   - 呼ぶところ: 翻訳が全部終わったときのトップ画面(ログイン中のみ)
6. **`/api/documents/[id]`(DELETE)**
   - リソース: 教材1件。`[id]` の部分に教材の番号が入る。その教材を消す(本人の教材だけ)。
   - 呼ぶところ: 履歴の詳細画面の削除ボタン(`src/components/DeleteDocumentButton.tsx`)
7. **`/api/tts`(POST)**
   - 処理の窓口。英文を受け取り、ElevenLabs で音声を作って返す。許可したアカウントだけが使える。
   - 呼ぶところ: 例文カードの再生ボタン(`src/components/SentenceCard.tsx`)

### API ではないもの
履歴の一覧(`/history`)と詳細(`/history/[id]`)は、API ではなく画面。サーバー側でその画面を作るときに、DB を直接読んでいる。そのため、「教材を読む `GET /api/documents`」はない。

### 作る予定のもの(ストリーミング PR 2)
8. **`/api/translations`(POST)**
   - リソース: 翻訳(1回分の翻訳の仕事)。POST は「翻訳を1件始める」という意味になる。
   - 今の `extract`・`process`・`documents` の3つが行っている仕事を、サーバーの中で一度に行う。
   - 呼ぶところ: PR 3 で画面を切り替えたあと、トップ画面から1回だけ。PR 5 で `/api/process` と `/api/extract` を消す予定。

### 整理して見えること
1. 名前の付け方が2種類ある。`documents`・`usage`・`translations` は「もの」の名前。`process`・`extract`・`tts` は「すること」の名前で、「処理を頼む窓口」になっている。小さなアプリではよくある形。
2. `/api/process` は、1つの URL で2つの違う仕事をしている。どちらの仕事かは、URL ではなく送る中身を見ないと分からない。新しい `/api/translations` はこれをやめ、「翻訳」というものを1件作る形にしている。
3. 「もの」の形にしておくと、あとで広げやすい。たとえば #63 の「後日やること」の取り直しは、`GET /api/translations/[id]`(この翻訳の、ここまでの結果を読む)という自然な形で足せる。
4. `extract` や `tts` は、何かを作るわけではないのに POST にしている。理由は2つ。
   - GET は「読むだけで、何も変えない。何回呼んでも同じ」ことが約束。費用がかかる処理(Claude や ElevenLabs の呼び出し、使用量の予約)には向かない。
   - GET では、大きなデータ(ファイルなど)を送れない。

## 関連する制約

- Vercel の関数が受け取れる本文には、上限がある(約4.5MB)。ファイルは base64 にすると約1.3倍になるので、**約3.4MB を超える PDF は、今のコードではアップロードできない**と考えられる(未検証)。
